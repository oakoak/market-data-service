# Open Risks / Unresolved Items

1. **Binance ToS — checked (September 2026), risk confirmed.** Document `binance.com/en/terms`, `Restrictions` section (SPA, direct fetch unavailable — text reconstructed via search index and related official sources, reproduces consistently, but the exact clause number in the current numbering is not directly confirmed). Without Binance's written consent, the following are prohibited: *"Trading services that make use of Binance quotes or market bulletin board information"*, *"Data feeding or streaming services that make use of any market data of Binance"*, *"Any other websites/apps/services that charge for or otherwise profit from ... market data obtained from Binance"*. This wording literally describes our model (hosted REST/WS API + MCP monetized on normalized Binance data, see [MVP decisions](./03-mvp-scope.md), [Binance map](./04-architecture/exchanges/binance.md)) — falls under points 2 and 3. A separate API-specific `PROD-TERMS-OF-USE` on `developers.binance.com` references the same document and provides no different redistribution rules; there is no public official Binance position on this (a thread on `dev.binance.vision` went unanswered by Binance staff).
   - **Reduces but does not remove the risk**: transformation/normalization (point-in-time reconstruction, unified schema, incidents) instead of raw passthrough — analogous to Tardis.dev's policy toward its own clients (redistribution banned except for 10-minute+ aggregates) and CoinAPI's (resale/rehosting of raw data banned, derived outputs allowed). Binance's wording is broader ("any market data"), with no explicit raw/derived distinction.
   - **Observed market behavior**: competitors from the market analysis (Amberdata, CoinAPI, CryptoCompare, Coinalyze) have publicly resold Binance data for years with no public lawsuits/enforcement found specifically on this point — not a legal guarantee, but it lowers the likelihood of practical enforcement at MVP scale.
   - **Forward-looking reference**: Kaiko explicitly states it has formal redistribution license agreements with exchanges instead of relying on public ToS interpretation — worth moving toward this model when transitioning from MVP to paying customers at scale.
   - **Plan decision**: the MVP plan is unchanged — the validation stage with 5-10 users ([MVP decisions](./03-mvp-scope.md)) carries low risk at this scale. Written permission or a formal data-licensing agreement from Binance business/BD is mandatory before monetization/scaling.
2. **Collector redundancy — resolved for MVP**: we accept the single-point-of-failure risk, ×2 duplication ([Architecture Overview](./04-architecture/00-overview.md) §6.1) is deferred. Reason — the single-process model already matches the MVP server's resource constraints ([collector stack](./04-architecture/01-stack.md), systemd `Restart=always` on a single instance); a second parallel collector on the same server provides no real fault tolerance (the shared point of failure is the machine itself), only extra load. Revisit when moving to separate infrastructure.
3. **NTP/clock accuracy** — collection servers must be NTP-synchronized and monitored for drift, otherwise dual-timestamp is just a marketing phrase.
4. **Rate limits/IP bans** — REST polling (funding/OI, bulk dumps) is subject to exchange limits; scaling to 100+ exchanges will require a backoff policy and possibly multiple outbound IPs.
5. **Storage growth and egress cost estimate** — need a GB/day-per-instrument-per-exchange estimate before locking in retention and tier pricing.
6. **Nest Exchange / equity-perps** — a separate regulated Binance entity (ADGM), likely a separate API host from the standard `fapi`/`fstream`. Not included in MVP scope pending a separate infrastructure check.
7. **Bybit ToS — checked (September 2026), risk confirmed, comparable to Binance.** Document: Bybit "API Terms and Conditions" (APIA) at `bybit.com/legal/service-specific-terms/API-Terms` (last updated 2026-01-16; a JS-rendered SPA — Sections 1-4 fetched and verified verbatim, Section 6 "Negative Conduct" corroborated via search-engine extraction and a third-party open-source Bybit API client repo, not hand-verified full-text — medium-high confidence). Section 3 defines "**Service Data**" broadly, as "any data, or information within the dataset and content that is given by using the API" — no raw/derived distinction, similar to Binance. Section 6 reportedly states the API client **"shall not... repackage or resell the services, or any part thereof, API or Service Data"** and **"shall not commercially exploit the APIs"** — this directly targets our hosted, monetized resale model, functionally equivalent to the Binance restriction (see item 1) though phrased via undefined "Service Data" rather than Binance's enumerated data types.
   - **Scraping the history-data portal**: no Bybit-specific clause names `bybit.com/derivatives/en/history-data` (needed to automate order-book snapshot backfill, see [Bybit map](./04-architecture/exchanges/bybit.md)). Bybit's general Terms of Use/Platform Terms (same legal family as the sibling Web3 User Agreement) carry standard anti-scraping language — barring *"any robot, spider, site search/retrieval application, or other manual or automatic device or process to download, retrieve, index"* content, plus a ban on framing/mirroring without written authorization. This reads as a general, site-wide prohibition, not one targeted at this specific portal, but it still covers automating downloads from it.
   - **Plan decision**: same posture as the Binance item — plan unchanged for the 5-10 user validation stage; written permission from Bybit is needed before scraping `history-data` at any volume, and before monetizing/scaling the resale of Bybit-sourced data.
