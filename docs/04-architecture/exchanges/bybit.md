# Bybit — Instrument and Data Source Map (spot + linear + inverse)

Second collection slice, following the same pattern as [the Binance map](./binance.md). Verified against the Bybit V5 API documentation and live responses from `api.bybit.com` (September 2026). Options, dated futures, and Event Contracts are out of this slice.

**Instruments:**
- **Spot**: BTCUSDT, ETHUSDT, SOLUSDT, XRPUSDT, DOGEUSDT, BTCUSDC, ETHUSDC. USDC pairs are a second quote currency with separate liquidity; how significant they are by volume (analogous to FDUSD on Binance) has not been verified.
- **Linear perp** (`category=linear`): BTCUSDT, ETHUSDT, SOLUSDT, XRPUSDT, DOGEUSDT, ADAUSDT, AVAXUSDT, BTCPERP, ETHPERP, XAUUSDT, XAGUSDT. There is no separate category for USDC contracts: `linear` covers both USDT and USDC, the difference is only in `quoteCoin`/`settleCoin`. **USDC-perps are named `{BASE}PERP`, not `{BASE}USDC`**: `BTCUSDC` under `linear` returns `10001 symbol invalid` (that symbol only exists in spot).
- **Inverse perp** (`category=inverse`): BTCUSD, ETHUSD. No `_PERP` suffix like Binance uses. The same category also contains dated inverse futures (`BTCUSDZ26`), so they must be filtered out with `contractType=InversePerpetual`, otherwise auto-discovery of instruments will pick them up for collection.
- BNB, LINK, and 1000PEPE, which are in the Binance slice, are not included here: their presence on Bybit has not been checked.

**Technical details:**
- **WS — a separate URL per category**: `wss://stream.bybit.com/v5/public/{spot|linear|inverse}`. Unlike Binance, the protocol is identical across all three segments, only the URL and subscription limits differ. Regional domains (`bybit.tr`, `bybitgeorgia.ge`, etc.) only concern accounts from those jurisdictions; the collector connects to the global `stream.bybit.com`.
- **Heartbeat is needed at the application level**: the client must send `{"op":"ping"}` every 20s, otherwise the connection closes after 10 minutes without traffic. The protocol-level ping that `websockets` sends automatically (see [collector stack](../01-stack.md)) is not enough here; the collector needs a dedicated coroutine.
- **A single WS subscription to `tickers.{symbol}` covers funding, mark/index price, and open interest** (`fundingRate`, `nextFundingTime`, `fundingIntervalHour`, `markPrice`, `indexPrice`, `openInterest`, `openInterestValue`). Unlike Binance, there is no mandatory REST polling for OI. It's unverified whether `tickers` arrives on derivatives as snapshot+delta (only changed fields); if so, the normalizer must keep the last known state per symbol.
- **Liquidations: `allLiquidation.{symbol}` is a full tape**, in batches roughly every 500ms. The old `liquidation.{symbol}` (max 1 message per second per symbol, the same defect as Binance's `forceOrder`) was replaced 2025-02-20, its documentation page now returns 404. Bybit does not have the `liquidation_partial_coverage` limitation (see the [Incidents schema](../00-overview.md#631-incidents-schema)). Completeness is only confirmed by Bybit's own claim and press coverage; worth cross-checking against our `forceOrder` archive for BTC. The `p` field is the bankruptcy price, not the execution price — the normalized schema must separate these explicitly.
- **Order book changes in 2025**: Level 1000 added (2025-08-14, pushed every 200ms), Level 500 removed for futures (2025-09-11), `orderbook.1` now only sends snapshots. Legacy API V3 was disabled 2024-08-31, V5 is the only API.
- **No Nest Exchange equivalent**: TradFi perps (XAUUSDT, XAGUSDT and others, launched spring 2026) run on the same V5 API and the same host, distinguished only by the `symbolType: "commodity"` field (not in the enum documentation, only visible in live responses). **`markPrice`/`indexPrice` freeze behavior outside gold/silver trading hours is unconfirmed by documentation** — Bybit's index/mark-price methodology docs describe a wider deviation threshold for XAUUSDT/XAGUSDT (~3% vs ~1% for BTC/ETH) and a fallback to last-traded/bid-ask price when a "reasonable spot price" isn't available, which is architecturally consistent with a freeze but not an explicit stated rule. A live poll on a regular trading day (2026-09-13) was inconclusive — `indexPrice` held constant across an 8s window, `markPrice` ticked, but that's expected during active hours and doesn't confirm weekend/holiday behavior. Best-informed guess: **likely yes**, given the same COMEX/LBMA-style reference as Binance. The `reference_price_freeze` detector should be enabled for these symbols regardless of confirmation; verify empirically by polling `GET /v5/market/tickers?category=linear&symbol=XAUUSDT` across a weekend before relying on this in incident logic.

**Data → source map:**

| Segment | Trades | Order book L2 | Funding + mark/index price | Open Interest | Liquidations |
|---|---|---|---|---|---|
| Spot | WS `publicTrade.{symbol}` | WS `orderbook.200.{symbol}` (snapshot+delta) | — | — | — |
| Linear perp | WS `publicTrade.{symbol}` | WS `orderbook.200.{symbol}` | WS `tickers.{symbol}` | WS `tickers.{symbol}` (history — REST `GET /v5/market/open-interest`) | WS `allLiquidation.{symbol}` |
| Inverse perp | WS `publicTrade.{symbol}` | WS `orderbook.200.{symbol}` | WS `tickers.{symbol}` | WS `tickers.{symbol}` | WS `allLiquidation.{symbol}` |

**Book depth — decided: `orderbook.200`**, uniformly across spot/linear/inverse (arrives every 100ms, like Binance's `@depth@100ms`). `orderbook.1000` (deeper, but every 200ms) is deferred rather than adopted now: at roughly 2.5x the uncompressed byte volume for levels that mostly capture stale/thin resting orders past the top of book, it adds cost without meaningfully improving point-in-time reconstruction fidelity for the realistic query patterns ([MVP decisions](../../03-mvp-scope.md)) — backtesting, TCA, BBO-adjacent analytics — while `orderbook.200`'s tighter 100ms cadence better serves the part of the book that actually matters for those queries. Using one depth across all three categories also keeps the delta-encoding/ingestion code path uniform. Revisit `orderbook.1000` as an opt-in, symbol-specific upgrade (e.g. BTC/ETH majors) once storage/bandwidth headroom and customer demand for deep-book fidelity are established — this recommendation is reasoned from documentation and known trade-offs, not from empirical production traffic measurement, which wasn't possible to obtain before implementation.

**Order book bootstrap + reconciliation — mechanism differs from Binance:**
1. Subscribe to `orderbook.{depth}.{symbol}`. The first message, `type: "snapshot"`, is the full book state — **no REST snapshot is needed to start**.
2. Then `type: "delta"` messages follow: size `"0"` removes a level, any other value inserts or updates it.
3. `u == 1` means the Bybit service restarted and a new snapshot arrived: the local book must be fully rewritten. This is the only resync rule documented officially.
4. **There is no explicit continuity rule**: no analog of `pu` or the `U <= lastUpdateId+1 <= u` formula, and no synchronization section in the documentation either. `seq` is described as a cross sequence for comparing different depths of the same book, not as a counter for detecting breaks. In practice (community SDKs, **officially unconfirmed**), implementations check that `u` increments by 1 message to message, and resubscribe on a jump. Resubscription (`unsubscribe`→`subscribe`) delivers a new snapshot and replaces a full REST resync.
5. On a `u` jump or restart (`u == 1`) we record an `orderbook_sequence_break` incident: `details` holds `u`/`seq` instead of `U`/`u`/`pu`, plus `resync_source: "ws_resubscribe"`.
6. `cts` is the matching time, from which we take `ts_exchange`; `ts` is the time the gateway sent the message.

Due to the loosely-specified documentation, the risk of silently missing a break is higher here than on Binance. So for Bybit it's worth adding a periodic reconciliation of the local book against REST `GET /v5/market/orderbook` every N minutes (cheap, see limits below), recording any discrepancy as an incident too.

**Connection strategy:** one topic per symbol for the book, one for trades, plus `tickers` and `allLiquidation` on derivatives. Total: spot 7×2=14, linear 11×4=44, inverse 2×4=8, roughly 66 topics. Each category already lives on its own URL, so **one connection per category**, as with Binance. Limits: spot allows at most 10 `args` per `subscribe` request (subscriptions must be batched), linear/inverse have no args limit. The overall cap is 21,000 total `args` characters per connection, and we're far from it. New connections are capped at 500 per 5 min per domain, so reconnection is still done with backoff to avoid a reconnect loop.

**REST rate limit budget:**

| API | Limit | `orderbook` (limit up to 1000) | `open-interest` | `funding/history` |
|---|---|---|---|---|
| All categories (spot/linear/inverse) | 600 requests / 5s per IP, **shared pool** across all categories and hosts | no separate weight | no separate weight | no separate weight |

Unlike Binance, this is not weighted limits with separate pools per API, but a single per-IP request counter. Exceeding it gets a `403 access too frequent` and blocks the IP for at least 10 min. In live collection REST is barely needed (snapshots arrive via WS, OI via `tickers`); what remains is book reconciliation and backfill. Backfilling funding and OI goes through pagination and can burn through the entire limit, so throttling the backfill job here is mandatory, not just a config parameter like on Binance.

**Historical backfill (`public.bybit.com`):**
- `/trading/{SYMBOL}/{SYMBOL}{YYYY-MM-DD}.csv.gz` — raw trades for derivatives (linear, inverse, USDC-perps, TradFi), daily files only, no monthly ones. Depth: BTCUSD — since 2019-10-01, BTCUSDT — since 2020-03-25, other symbols — since their listing date.
- `/spot/{SYMBOL}/` — roughly 2000 spot pairs. **Confirmed: raw trades, not klines.** Sample verified by direct download (`BTCUSDT-2025-08.csv.gz`, ~117MB, ~16.7M rows): columns are `id, timestamp, price, volume, side` — individual executed trades, tick-level, no OHLCV/interval structure. Packaged **monthly** (`SYMBOL-YYYY-MM.csv.gz`), unlike the derivatives dumps below which are daily — a different cadence to account for in the backfill job. BTCUSDT history available from 2022-11.
- `/premium_index/` (inverse only), `/spot_index/`, `/kline_for_metatrader4/`.
- **No bulk L2 archive exists** (no analog of Binance's `bookDepth`). Order book snapshots since ~2023 exist only on the web portal `bybit.com/derivatives/en/history-data`, exports limited to 7 days at a time, ~65-100 MB/day per symbol. This can only be automated via scraping — checked against Bybit's ToS, see [Risks](../../05-risks.md) item 7: general anti-scraping language applies, written permission needed before scraping at volume.
- Funding and OI have no dedicated dumps, only REST pagination (`GET /v5/market/funding/history`, `GET /v5/market/open-interest`). `funding/history` has a quirk: passing only `startTime` without `endTime` returns an error.
