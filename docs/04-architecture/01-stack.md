# Collector Stack — Python (MVP)

Language chosen by preference/experience; below are the concrete libraries following the "dumb collector" principle from [Architecture Overview](./00-overview.md) (§6.2) — minimal dependencies, minimal parsing. This stack is exchange-agnostic; per-exchange specifics (custom heartbeat, resync rules, etc.) live in [architecture/exchanges](./exchanges/).

- **WS client: `websockets`**, not `aiohttp`. Both libraries handle exchange server-initiated protocol-level pings correctly without manual code, but `aiohttp` drags in an entire HTTP framework for one feature, while `websockets` is specialized, lightweight, and already solves backpressure for long-lived (24h+) connections. At our scale (5-10 connections for combined streams) the overhead difference doesn't matter — the "don't drag in more than needed" principle decides it.
- **Broker: Redis Streams**, reusing the same Redis already planned for the hot cache (§6.4), instead of a separate Kafka/NATS daemon — matches the MVP server's resource constraints. `redis.asyncio` provides mature consumer-group support (`XREADGROUP`/`XACK`/`XCLAIM`/`XAUTOCLAIM`) for message recovery after a processor crash. **Important caveat**: cache and broker on the same Redis conflict on eviction policy (the cache needs `allkeys-lru`, the broker needs `noeviction`, otherwise it can silently lose data under memory pressure). Solution — not one database: keep broker streams in a separate logical Redis DB (`SELECT`/separate `maxmemory`) with `noeviction` + active `XTRIM`/`MAXLEN`, and the cache in another with LRU. One Redis process, but separated roles and limits.
- **ClickHouse client: `clickhouse-connect`** — the official client from ClickHouse Inc, best maintained. Since version 0.12.0 (March 2026) natively async (I/O on aiohttp, a separate thread pool only for CPU-bound response parsing) — batch inserts from the asyncio processor don't need to be wrapped in `asyncio.to_thread`.
- **Process supervision**: a systemd unit with `Restart=always` — the simplest option for a single server, without extra tooling (Supervisor/Docker orchestration are overkill at this stage).
